# Service level targets

Service-project administrators configure calendars and goals from **Agent queues → SLA settings**. Each publication creates an immutable version. A goal references a specific calendar version; publishing new hours does not rewrite existing cycles. Goal ordering is ascending, first matching goal per RESPONSE/RESOLUTION metric. Disabled goals do not start future cycles.

Calendars use an IANA timezone, seven weekday arrays (Sunday first), minute ranges `[start,end)`, holiday dates, and date-keyed exceptions. Split overnight windows across days. Exceptions override holidays. Calculations count actual elapsed working minutes: skipped DST time contributes nothing and repeated local time contributes twice. Targets are reached at the exact deadline, including partial minutes.

Goal conditions are AND comparisons `{field,equals}` over request type, priority, organization, label ID, status, status category, event, and configured custom-field IDs (`field:ID`). Timer rules provide start, stop, reset, success, resume conditions and independently named pause reasons. All active pause reasons must clear before time accrues again; time spent under overlapping pauses is not counted twice. Default resolution goals stop at DONE; default response goals stop at an explicit customer-response confirmation. Internal agent comments do not count as customer contact. Agents can confirm an already-sent response with an audited explanation; that action does not send email.

SLA signals are captured transactionally for service creation, all issue mutation paths, request reclassification and customer replies. Deferred database triggers capture final custom fields/labels at commit. A request-level lock serializes signal timestamps with the worker clock. The worker processes at most 100 pending signals per request, never ticks beyond unprocessed history, and selects at most 25 requests per batch. The `sla-worker` Compose service runs every five seconds; `pnpm sla:worker --once` performs a one-shot recovery pass inside Docker. Keep it running in deployments. Worker batch/failure logs contain operational counts/codes, not customer content.

Each cycle retains its goal/calendar version, pause reasons, accrued business time, exact risk/breach times and immutable lifecycle events. Reopening creates a new cycle without changing previous results. Retries deduplicate history, escalation jobs, webhook deliveries and notifications. Subscribe to `sla.risk`, `sla.breached`, and `sla.succeeded` for pre/post-deadline automation and webhooks. Integration tests only inspect local outboxes.

Queue snapshots can include SLA goal and remaining-time columns. Issue targets and reports recheck project permissions and issue security. Reports cover 1–365 days with a 10,000-cycle limit. Portal summaries require current customer authorization and explicit `portalVisible`; they expose only the approved label, plain-language state, remaining business minutes and last update, not internal conditions, pause reasons, IDs or history. Values are persisted worker observations, not a browser-side reconstruction. SLA history is available through the issue target API; project reporting is available at `/api/projects/{key}/sla/report?days=90`.

Docker checks include timezone gaps/folds, holidays, partial minutes, overlapping pauses, delayed/restarted processing, version immutability, reopening, transactional API/worker writes, outbox deduplication, tenant validation and browser accessibility.
